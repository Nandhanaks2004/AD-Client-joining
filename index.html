Core Concepts

Active Directory Objects

Everything in AD is an object. Each object has attributes, a unique identity, and a specific role in the enterprise hierarchy.

👤
User Objects
Represent individual enterprise identities. Store username, password hash, email, department, phone, and login restrictions. The foundation of all authentication.
CN=jdoe,OU=IT,DC=hackverse,DC=local
👥
Group Objects
Bundle users with shared permissions. Instead of assigning access to 100 users individually, assign it to one group. Security groups control access; distribution groups handle email.
Security / Distribution Groups
🖥
Computer Objects
Created when a machine joins the domain. Allows centralized management, remote administration, policy targeting, and machine authentication using Kerberos.
WIN10-PC01$@hackverse.local
📁
Organizational Units
Containers that organize all other objects into logical departments. OUs are the primary targets for Group Policy application and delegation of control.
OU=HR,DC=hackverse,DC=local
Organizational Design

Organizational Units (OUs) — Why They Exist

OUs are the filing system of Active Directory. Without them, all 10,000 objects in a large enterprise would exist in a flat, unmanageable chaos.

Enterprise Analogy
An OU is like a department in a company. Just as a company has HR, IT, Finance, and Security departments — each with their own physical spaces, access restrictions, and managers — Active Directory uses OUs to mirror this structure digitally. Each OU can have its own policies, its own delegated administrator, and its own set of objects.

Permission Management

Group Management — Why Groups Matter

Groups are the scalable layer between individual users and resource permissions. They are central to enterprise access control architecture.

Enterprise Analogy
Groups work like "All Staff" email lists in a company. Instead of emailing 500 people individually, you email the group. In AD, instead of giving 500 users access to the Finance share individually, you put them in "Finance-ReadOnly" group and give the group access. Adding a new employee is just adding them to the group — they instantly inherit all permissions.
Without Groups
100 Users, 100 Manual Assignments
Each user given permission to Finance Share individually
New employee? Add permission to every resource one-by-one
Employee leaves? Hunt down every permission assigned to them
Zero scalability — administrative nightmare at enterprise scale
With Groups
Group → Permission Once, Scale Forever
Finance-ReadOnly group gets permission to Finance Share
New employee? Add to group → Inherits all permissions instantly
Employee leaves? Remove from groups → All access revoked instantly
100% scalable — same process for 10 or 10,000 users

Domain Client Joining — Full Process

Joining a Windows client to the domain is what connects an isolated workstation to the centralized AD infrastructure. Walk through every step and the DNS dependency that makes it work.

Critical Prerequisite
Before joining: the client's DNS server must point to the Domain Controller. Without this, the client cannot resolve "hackverse.local" to an IP address, the DC cannot be contacted, and the domain join will fail with "Domain not found" error.

Security Internals

Machine Trust Relationship

When a computer joins the domain, it is not just a configuration change — a cryptographic trust relationship is established between the machine and the Domain Controller.

Windows 10 Client Requests Domain Join
↓
Computer Object Created in AD (Computers OU)
↓
Machine Account Password Auto-Generated (120 chars, rotates every 30 days)
↓
Trust Relationship Established: Client ↔ DC
↓
Authentication Switches: Local SAM → Kerberos ✓
🖥
Computer Object Created
CN=WIN10-PC01 created in Computers container. Object stores: machine name, OS version, last logon, and group memberships. Visible in ADUC → Computers.
🔑
Machine Account Password
A 120-character machine account password (WIN10-PC01$) is automatically generated and stored in AD. It rotates every 30 days — managed automatically without admin intervention.
🤝
Trust Established
The machine can now authenticate to the domain using its machine account. This trust is required before any user can log in with domain credentials on this machine.
🔐
Kerberos Replaces Local Auth
After joining, domain logins use Kerberos protocol instead of the local SAM database. The DC becomes the authentication arbiter for this machine permanently.
Pentesting Relevance
The machine trust relationship is critical in attacks like Pass-the-Ticket, Silver Ticket, and Machine-in-the-Middle attacks. If the machine account password is extracted, an attacker can forge service tickets for that specific machine — bypassing normal user authentication entirely.
Authentication Protocol

Introduction to Kerberos Authentication

After a machine joins the domain, all authentication switches from local (NTLM/SAM) to Kerberos — the enterprise-grade ticket-based authentication protocol used by Active Directory.

Why Kerberos?
Kerberos never sends passwords over the network. Instead, it uses encrypted tickets as proof of identity. Think of it like an airport boarding pass — you show the ticket (not your passport) to board each flight (access each resource). The ticket proves who you are without revealing your secret.
Client Machine
1. User enters hackverse\student1
2. Sends AS-REQ to KDC
3. Receives TGT (Ticket Granting Ticket)
4. Uses TGT to request service tickets
5. Presents service ticket to resource
6. Access granted without password

Cybersecurity Context

AD Security Relevance & Pentesting Bridge

Active Directory is the #1 target in enterprise penetration tests. Understanding why requires knowing exactly what compromising AD gives an attacker.

Attacker Compromises Single Domain User
↓ Kerberoasting / Credential Dump
Privilege Escalation → Domain Admin
↓
Domain Controller Compromised
↓ DCSync / NTDS.dit Dump
All 500 User Password Hashes Extracted
↓
Complete Enterprise Compromise 💀
AD Enumeration
First step after gaining any domain foothold. Map users, groups, OUs, GPOs, and trust relationships using tools like BloodHound, ldapdomaindump, or PowerView.
Kerberoasting
Request service tickets for SPNs, extract the encrypted ticket offline, crack the service account password without touching the DC or triggering traditional alerts.
Pass-the-Hash / Ticket
Use extracted NTLM hashes or Kerberos tickets to authenticate as another user without knowing their plaintext password. Bypasses standard authentication completely.
DCSync Attack
If Domain Admin access is obtained, simulate a DC replication request to extract all password hashes from NTDS.dit — effectively dumping the entire identity database.
Golden Ticket
With the krbtgt hash, forge a Kerberos TGT for any user in the domain — including Domain Admins — giving perpetual, unrevokable access even if passwords change.
GPO Abuse
Modify Group Policy to deploy malware, create local admin accounts, or disable Defender across all domain machines simultaneously — affecting the entire organization at once.
